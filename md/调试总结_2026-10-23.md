## 【10-23 傍晚 · 打火导致 EPS 故障 LKA_STATE=17 的完整闭环】★★★

**症状**：转向跑通后试驾，**热重启(EON+panda 已开机时熄火再打火)后 engage 会报 "steering temporarily unavailable"，转向失效**。

**诊断过程(全部实测验证)**：
1. 用正确位宽解码 0x262(`LKA_STATE : 31|7@0+` → `(byte3>>1)&0x7F`，之前错用 `&0x7` 把 9/17/25 都截成了别的值)，确认 EPS 卡在 **非标状态码 17**(DBC 只定义 1/5/9/25，这台是非标老 EPS)。
2. `steerWarning = lka_state not in (1,3,5)` → 17 命中告警；[controlsd.py](../selfdrive/controls/controlsd.py) `lat_active = active and not steerWarning ...` → **openpilot 直接不发转向 + `steerTempUnavailable` 软退出**。
3. **17 不是对命令的反应，是 EPS 自己латch 的故障**：openpilot disabled、EON 软重启、点火循环，17 都不消失。
4. **把 17/19 加进允许表是错的**(实测"17 不给 steering")——只是藏了告警，让 openpilot 对故障 EPS 空发命令，已回退。

**根因(对照实验铁证)**：
| 断电瞬间 `STEER_REQUEST` | EPS 恢复后 |
|---|---|
| **1**(engaged，LKA 命令进行中被硬断电) | ❌ **17 故障** |
| **0**(先按 CANCEL 干净脱离再断电) | ✅ **1 standby 健康** |

→ **EPS 在"LKA 命令进行中(STEER_REQUEST=1)"被粗暴断电会латch 保护故障 17。** 真 Corolla 熄火有优雅关断序列(摄像头先停 LKA、模块按序休眠、最后断电)，单 CAN 去掉摄像头后缺了这个。openpilot 的"脱离"没有专门终止报文——就是持续的 0x2E4 里把 `STEER_REQUEST` 位从 1 翻 0、torque 清零。

**预防**：
- **操作**：熄火/断电/打火前**先按 CANCEL 脱离**(STEER_REQUEST→0)→ EPS 干净回 standby，不会进 17。✅ 实测验证
- **代码(待实现)**：智能自动 engage 门控(上电后等 EPS 报健康 standby 再挂)；可选 Arduino 电压检测掉电前自动拉低 CRUISE_ACTIVE。

**恢复(已故障时)**：openpilot 不发命令(脱离/自动 engage 关)的前提下，**干净长断电几分钟**(放电)→ EPS 复位到 standby(1)。✅ 实测验证

**调试工具沉淀**(session 工作区)：`crank_monitor.py`(LKA_STATE/can_age/engage 轨迹)、`tuning_logger.py`(调参数据，但 6-socket 会被 msgq eviction，改用解析 loggerd 的 rlog 更稳)。

**结果**：修复 + 正确操作流程后再试驾，**横向控制表现"非常完美"**。

> 注意：当前 Arduino 固件 `AUTO_ENGAGE_ON_OP=false`(手动按 MAIN engage)。因为自动 engage 可能在 EPS 刚上电/故障时就发命令，手动挂上更安全;下一步可做"智能门控自动 engage"。

## 【10-23 下午 · 根因找到并修复】EPS 终于进入 LKA_STATE=5 (ACTIVE) ★★★

**一句话：真正的根因是 panda 的 bus0→bus2 转发在单 CAN(无摄像头 bus2)上把整个 TX 堵死，导致 openpilot 的 0x2E4 从没到过物理总线、EPS 从没收到过转向命令。禁掉该转发后，EPS 从 LKA_STATE=3 → 1 → 5 全链路打通。**

### 诊断链条（如何定位的）
1. 给 Arduino 固件加 `pump_rx()`（每次 TX 后读空 MCP2515 RX 缓冲，根治总线繁忙时的整类丢包）+ `0x702` 诊断帧（上报收到过哪些地址）。
2. 实测：Arduino 能收到真实 EPS 的 `0x25/0x260/0x262`，但 **openpilot 的 `0x2E4/0x343/0x412` 一帧都收不到** → openpilot 的全部 TX 都没上总线。
3. 停 openpilot、panda 设 `SAFETY_ALLOUTPUT` 直接发测试帧：
   - `ALLOUTPUT` 下发 `0x2E4` 到 bus0 → Arduino **收到**（证明物理 TX 没坏）。
   - 切到 `SAFETY_TOYOTA` 再发 → `can_send` 直接 **USB 写超时**（panda 根本不接收 TX）。
4. 结合 `canFwdErrs=2,429,657`：Toyota 安全模式会把 bus0 每帧转发到 bus2；单 CAN 没有 bus2 → 转发帧永远得不到 ACK → CAN2 无限重传 → panda TX 队列被堵死 → openpilot 的 bus0 TX 排不进去。

### 修复
- `panda/board/safety/safety_toyota.h` 的 `toyota_fwd_hook`：把 `bus_num==0` 时的 `bus_fwd = 2` 改成 `-1`（单 CAN 不转发）。
- 重新编译 panda 固件（EON 上有 `arm-none-eabi-gcc`+`scons`）→ reboot → `pandad` 自动按签名变化刷入。
- 补丁已存为 `patches/panda_toyota_single_can_no_fwd.patch`（panda 子模块指向 commaai 上游、无法直接 push，故用 out-of-tree patch 固化）；EON 上同时提交在 panda 子模块分支 `single-can-nofwd`。

### 修复后实测（稳定 8s 零抖动）
| 指标 | 修复前 | 修复后 |
|---|---|---|
| `canFwdErrs` | 2,429,657 | **0** |
| Arduino 收到 `0x2E4/0x343/0x412` | 0 | **全部收到** |
| openpilot `state` | disabled | **enabled / active=True** |
| `pandaControlsAllowed` | False | **True** |
| 真实 EPS `LKA_STATE` | **3**(未定义) | **5**(ACTIVE) |

> 注：静止 `vEgo=0` 时 steer≈0、方向盘不动是正确的。要测真实转动需模拟车速或力矩注入（见任务 1，涉及方向盘实际转动的安全测试）。

### 本次新增/修改（除 panda 固件外）
- `ECU/ECU_fixed_option1_tolerant.ino`：新增 `pump_rx()` 根治 MCP2515 RX 溢出丢包；新增 `0x702` 诊断帧（ever_2e4/25/260/262/343/412 + last_rx_id）。
- `patches/`：panda 补丁 + 应用说明 README。

## 【10-23 上午续】自动 engage 调试进展

- **Arduino 的 CAN 接收（RX）其实是正常的**：通过新增的 `0x701` 心跳帧在车上实测，`rx_any_ever=1`、`rx_2e4_ever=1`，确认 Arduino 收到了总线帧、也收到了 openpilot 的 0x2E4。之前“RX 坏了”的判断是错的。
- **bench 上 `CAN_BEGIN_FAILED` 的原因**：bench 上没接 CAN 模块（MCP2515），不是硬件坏。必须上车（接 CAN 总线+供电）才能测。
- **自动 engage 没触发的真正原因是逻辑 bug**：原判据“连续 500ms 内持续看到 0x2E4、累计 2 秒”被 Arduino 主循环抖动（0x2E4 只零散收到 ~8帧/秒）不断清零，永远攒不满。
- **已修复**：改成「累计收到 `AUTO_ENGAGE_MIN_2E4=40` 帧 0x2E4 就一次性 engage」，并让每轮循环多读几帧 RX（最多 8 帧）加快计数、减少 MCP2515 缓冲溢出丢包。
  - 用帧数触发也更正确：收到 0x2E4 就证明 openpilot+boardd 已在跑、且已收过我们的 CRUISE_ACTIVE=0，上升沿干净。
- **状态**：修复固件已编译，等 Arduino 接回 USB 烧录（上午烧录时 COM4 多次因端口占用失败，Arduino 在车上/USB 断开时也无法烧）。
- **一次性语义确认**：每次 Arduino 上电只自动 engage 一次（`auto_engaged_done`），刹车/Cancel 退出后不自动重挂，需重新上电或手动按 MAIN。
- **0x701 心跳帧**（调试用）字节定义：
  `[0]=rx_any_ever [1]=rx_2e4_ever [2]=op_steer_req [3]=auto_engaged [4]=OP_ON [5]=rx_any_count&0xFF [6]=rx_2e4_count&0xFF [7]=op_seen_since!=0`

### 坑补充
- **烧录 COM4 常因端口瞬时占用失败**：重试一次通常就好；Arduino 在车上且 USB 断开时根本枚举不出来（只剩蓝牙 COM8/COM9）。
- **bench 调 CAN 必须接上 MCP2515 模块**，否则 `CAN.begin()` 直接失败，测不了收发。

## 二、最重要的认知纠正（避免明天再走弯路）

### 1. `can2e4 = 0` 根本不是故障证据 ❗❗❗
- 之前整段调试都基于“sc2e4 在涨、can2e4=0，所以命令没上总线”——**这个前提是错的**。
- **panda 的 CAN 控制器硬件上不会把自己发出去的帧回灌到接收流**。
- 所以 openpilot 自己发的 0x2E4，**永远不会**出现在 openpilot 自己“接收到的 can”里，无论它有没有真的上总线。
- 正确的 TX 验证指标是 `pandaState.canSendErrs`（实测=0，表示发送被总线 ACK，即真的发出去了）。

### 2. “真实总线”这个说法在单总线拓扑下不成立
- 用户只有一条物理 CAN，所有节点并在一起。不存在“另一条 steering bus”。
- 收到的所有车侧帧都在 `src=0`（bus 0）。openpilot 也在 bus 0 发 0x2E4。TX/RX 同一条总线，EPS 就在这条线上。

### 3. 静止时“不转向”是正常的，不是 bug
- `vEgo=0` 时横向控制输出力矩≈0（没有可跟踪路径），`actSteer=0`、`tqMax=0`。
- 要测执行必须有车速或用“受控力矩注入”。

### 4. panda 的 engage 是“上升沿锁存”
- `safety_toyota.h`：`controls_allowed` 只在 0x1D2 的 bit5(CRUISE_ACTIVE) 发生 `0→1` 跳变时置 1。
- Arduino 把 CRUISE_ACTIVE 恒定保持为 1 → EON 重启后（Arduino 没断电）panda 收不到跳变 → 永远挂不上。
- **规避：开机后必须手动做一次 关→开（按 MAIN 关掉，停 2 秒，再按 MAIN 打开）制造跳变。**

## 三、关键实测证据

### EPS 执行测试（engage + 注入 -150 力矩，12 秒）
```
active=True ctrlAllowed=True  cmdTqMax=-150  REQ1=2374(持续)
angSpan=0.0      ← 真实角度传感器 0x25 完全不动
realLKA={3}      ← 真实 EPS 一直停在 LKA_STATE=3，没进 active(5)
epsTq[0..23]     ← EPS 力矩传感器 0x260 只有基线噪声，对命令无反应
```
→ openpilot 把 -150 力矩真的发到了 EPS 所在总线，但 EPS 拒绝执行。

### LKA_STATE 官方定义（opendbc toyota_nodsu_pt_generated.dbc）
```
VAL_ 610 LKA_STATE 25 "temporary_fault" 9 "temporary_fault2" 5 "active" 1 "standby";
```
- **没有 3 这个值。** 真实 EPS 报的 `LKA_STATE=3` 是未定义/异常状态，连 standby(1) 都不是。
- 注意：stock openpilot 对 `lka_state not in (1,5)` 会判 steerWarning；我们在 single_can 里把 3 也放行，掩盖了这个告警（见 carstate.py）。

### EPS 诊断（通过 panda 直连，SAFETY_ALLOUTPUT，offroad 下）
- EPS 诊断地址：请求 `0x7A1` / 响应 `0x7A9`
- `10 01`(默认会话) → `50` ✅；`3E 01`(tester present) → `7E` ✅ → **EPS 在线、能通信**
- `1A 82` → ASCII **"02B50"** → Toyota EPS 零件号后缀（89650-02B50，Corolla 系）→ **确认真实 Corolla EPS**
- `21 0B` → `61 0B 02 5D`（支持 Toyota 私有读数本地 ID 0x0B）
- **所有标准 DTC 服务都不支持**：`0x19`→7F19**11**, `0x18`→7F18**11**, `0x03`→7F03**11**, `0x13`→7F1312, `0x17`→7F1711
  - 即：这台 EPS 是老式/非标单元，**故障码只能用 Toyota Techstream 读，标准 CAN 诊断读不到**。

## 四、踩过的坑（Pitfalls）

1. **steering_watch 自启动把系统压爆 → 触发 commIssue 软退出。**
   - 早期加的 `run_steering_watch.sh` 自启动（`--duration 5400`）订阅大量 socket，导致 "evicting all subscribers" 和 `commIssue/softDisable`。
   - 已杀进程并把 `launch_env.sh` 里 `ENABLE_STEERING_WATCH_AUTORUN` 默认改为 `0`。
   - **教训：调试监控脚本不要常驻自启动。**

2. **Arduino 伪造 0x262 与真实 EPS 冲突。**
   - Arduino 原本发假 EPS_STATUS(0x262, LKA_STATE=5)，真实 EPS 也发 0x262(LKA_STATE=3) → ID 冲突，读到的值在 3/5 乱跳。
   - 已在 Arduino 加开关 `EMIT_FAKE_EPS_STATUS=false`（真实 EPS 在场时不伪造）。已重新烧录。

3. **env 变量传不进 controlsd。**
   - openpilot 的 manager launcher 会重置子进程环境，`launch_env.sh` 里 export 的变量 controlsd 读不到。
   - **改用持久化文件开关**：`/data/suppress_driver_monitoring` 存在则抑制 DM。
   - 教训：给 controlsd 传配置用 Param 或文件，别指望 env 继承。

4. **单独 kill controlsd 不会被 manager 自动拉起**（onroad 下也不行）→ 改代码后要 `reboot` 才能生效。

5. **PowerShell 调 ssh 时 `$()` 会被本地解析。**
   - 远端命令里凡有 `$(...)`、`\"` 一律改用：把脚本写进 here-string，`tr -d '\r' > /tmp/x.sh` 再 `bash`。

## 六、明天的工作计划（按优先级）

### 任务 0：Arduino 自动 engage（用户需求，优先做） ⭐
**目标**：Arduino 检测到 openpilot 已运行后，自动让系统进入 engage，不用每次手动按 MAIN。

**为什么需要特殊处理**（关键）：
- panda 的 `controls_allowed` 只在 0x1D2 的 CRUISE_ACTIVE 位发生 `0→1` 跳变时锁存（见坑 §四.4）。
- 如果 Arduino 一上电就把 CRUISE_ACTIVE 恒为 1，panda 永远收不到跳变 → 挂不上。
- 所以“自动 engage”不能简单把 CRUISE_ACTIVE 一直拉高，**必须在“确认 openpilot 已起来”之后，制造一次干净的 0→1 跳变**。

**如何判断 openpilot 已运行**：
- openpilot 的 carcontroller 一旦 controlsd 起来，就会以 ~100Hz **持续发送 0x2E4(STEERING_LKA)**（即使 disabled，也发 torque=0 的帧）。
- 所以 Arduino **监听总线上是否出现 0x2E4** 即可判定 openpilot 活着。
- 进一步：0x2E4 的 `byte0 bit0` = STEER_REQUEST。openpilot active 时=1，disabled 时=0 → Arduino 还能借此读出 openpilot 的真实 active 状态。

**推荐的最小安全设计（开机一次性自动 engage）**：
1. 开机：`OP_ON=false`（CRUISE_ACTIVE=0，已是默认值，保证干净低电平）。
2. Arduino 监听 0x2E4；连续稳定看到 ~2 秒（去抖，确认 openpilot 稳定运行）。
3. 条件满足且 `OP_ON==false` 且无刹车/油门 override 时：执行**一次** `OP_ON=false→true`，产生 CRUISE_ACTIVE 的 0→1 跳变 → 同时触发 panda 锁存和 openpilot 挂上。
4. 之后 MAIN / Cancel / 刹车 照常工作（刹车/油门仍强制 `OP_ON=false` 退出）。
5. **安全**：自动 engage 只做一次性（`auto_engaged_done` 标志）。刹车退出后不要自动立刻重挂（危险）。若要支持“掉线后自动重挂”，需额外条件并谨慎，默认先不做。

**代码落点（ECU_fixed_option1_tolerant.ino）**：
- 把 loop 末尾那段“收到就丢弃”的 RX：
  `if (CAN.parsePacket()) { while (CAN.available()) CAN.read(); }`
  改成**解析 0x2E4**：读 `CAN.packetId()`，若 ==0x2E4，取 byte0 → 置 `op_seen=true`、记录 `op_steer_req=(byte0 & 1)`。
- 新增状态：`uint32_t op_seen_since; bool auto_engaged_done=false;`
- 新增开关：`const bool AUTO_ENGAGE_ON_OP = true;`（方便关闭回退到手动）。
- 在按键/状态逻辑处加：若 `AUTO_ENGAGE_ON_OP && !auto_engaged_done && op 稳定2秒 && !OP_ON && !BRAKE_PRESSED && GAS_RELEASED` → `OP_ON=true; auto_engaged_done=true;`
- 注意：0x2E4 的接收时序不要阻塞主循环的发包节奏。

### 读真实 EPS 状态/诊断（需先 offroad 释放 panda）

### 关键监控指标
- `pandaState.controlsAllowed`、`canSendErrs`（TX 健康，不是 can2e4！）
- sendcan 0x2E4：`byte0&1`=STEER_REQUEST，`bytes[1:2]`=torque(signed)
- 真实 EPS：0x262 的 `byte3>>1`=LKA_STATE（真实=3，期望 active=5）
- 真实角度：0x25 解码（3|12@0- ×1.5），看 angSpan 是否变化
