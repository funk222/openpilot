## 1. 项目概述

**目标**：在老 C2 EON 上，用一套"grey panda + 单 CAN + Arduino Toyota 信号模拟器 + 真实 Corolla EPS"
的台架/改装方案，跑通 openpilot 的横向（LKA）自动转向。

**硬件拓扑**
- **EON（comma C2）**：跑 openpilot，自带内置电池（点火/打火时不断电）。
- **grey panda**：通过 OBD-II 直连**单一物理 CAN**。0.8.14 官方砍了 grey panda 支持，社区把它在
  boardd 里**伪装成 black panda**（`hw_type` 重映射）才能连上。
- **Arduino UNO + MCP2515**：Toyota 信号模拟器（发 PCM_CRUISE、轮速、按钮、车身报文等），
  同时在本项目中兼作**总线嗅探器**。
- **真实 Corolla EPS（带电机，非标老单元）**：挂在同一条物理 CAN 上。注意它用**非标 LKA_STATE 码**
  （不是 DBC 标准的 1/5/9/25），并且**不支持标准 DTC 诊断服务**。

**软件基线**：官方 0.8.13（tag commit `6ca0269f`），针对单 CAN + 老设备做定制。

### B. 速度显示偏高（已解决）
- 根因：轮速发送加了固定偏移 `+67.67 kph`，所有工况抬高 `WHEEL_SPEEDS`。
- 解决：改纯比例模型 `wheel_spd = speed * TOYOTA_WHEEL_SPEED_SCALE`（ECU 固件）。

### C. 驾驶员监控 / commIssue（已解决）
- **DM "没看到驾驶员"告警**：单 CAN 无驾驶员摄像头 → 用**持久文件开关** `/data/suppress_driver_monitoring`
  抑制（注意：manager 会重置子进程 env，env 方案无效，必须用文件或 Param）。
- **commIssue 软退出的真凶**：早期 `run_steering_watch.sh` 自启动订阅大量 socket →
  "evicting all subscribers" → commIssue/softDisable。**教训：调试监控脚本不要常驻自启动**，
  已把 `ENABLE_STEERING_WATCH_AUTORUN` 默认改为 `0`（提交 `b36a557d`）。

### D. ★★★ 转向根因：panda bus0→bus2 转发把 TX 堵死（已解决，核心突破）

**最终定论（一句话）**：grey panda 被伪装成 black panda 跑 Toyota 安全逻辑，而 **Toyota 安全会把
bus0 收到的每一帧转发到 bus2（摄像头）**；单 CAN 根本没有 bus2，转发帧永远得不到 ACK →
CAN2 无限重传 → **panda 的整个 CAN TX 队列被堵死** → openpilot 的 0x2E4/0x343/0x412
**从没真正发到物理总线** → 真实 EPS 从没收到过转向命令，一直卡在非标状态。

**是如何定位的（全部实测）**：
1. 给 Arduino 固件加 `pump_rx()`（每次 TX 后读空 MCP2515 两级 RX 缓冲，根治繁忙总线整类丢包）
   + `0x702` 诊断帧（上报收到过哪些地址）。
2. 实测：Arduino 能收到真实 EPS 的 `0x25/0x260/0x262`，但 openpilot 的 `0x2E4/0x343/0x412`
   **一帧都收不到** → openpilot 的全部 TX 都没上总线。
3. 停 openpilot、panda 设 `SAFETY_ALLOUTPUT` 直接发测试帧：`ALLOUTPUT` 下发 0x2E4 到 bus0
   → Arduino **收到**（证明物理 TX 没坏）；切 `SAFETY_TOYOTA` 再发 → `can_send` **USB 写超时**。
4. panda 健康：`canFwdErrs = 2,429,657`（240 万！）、`pandaType=blackPanda`、`harnessStatus=notConnected`
   → 坐实转发 jam。

**修复**：`panda/board/safety/safety_toyota.h` 的 `toyota_fwd_hook` 把 `bus_num==0` 时的
`bus_fwd = 2` 改成 `-1`（单 CAN 不转发）。重编 panda 固件 → reboot → `pandad` 按签名变化自动刷入。
- panda 是指向 commaai 上游的子模块、无法直接 push，故用 **out-of-tree 补丁**固化：
  `patches/panda_toyota_single_can_no_fwd.patch`（+ `patches/README.md`）；EON 的 panda 子模块
  也提交在本地分支 `single-can-nofwd`。

**修复后实测（稳定、零抖动）**：
| 指标 | 修复前 | 修复后 |
|---|---|---|
| `canFwdErrs` | 2,429,657 | **0** |
| Arduino 收到 openpilot 0x2E4/0x343/0x412 | 0 | **全部收到** |
| openpilot | disabled | **enabled / active** |
| `pandaControlsAllowed` | False | **True** |
| **真实 EPS `LKA_STATE`** | **3（未定义）** | **1→5（standby→ACTIVE）** |

> 相关提交：`7525dff4`（核心修复 + RX pump + 0x702 嗅探）。另 `36c738c3` 去掉了早期错误的
> "bus0+bus1 双发"（见 §3）。

### E. ★★★ 打火导致 EPS 故障 LKA_STATE=17（已闭环：根因/预防/恢复）

**症状**：转向跑通后，**热重启（EON+panda 已开机时熄火再打火）** → engage 报
"steering temporarily unavailable"，转向失效。冷启动则正常。

**正确解码**：`EPS_STATUS(0x262)` 的 `LKA_STATE : 31|7@0+` 是 **7 位**，正确解码
`(byte3>>1) & 0x7F`（早期误用 `&0x7` 把 9/17/25 都截断成别的值）。这台非标 EPS 用 **17** 表示一个
带故障位的降级态（`17=0b10001`，和标准故障码 9/25 一样带高位 bit）。

**故障链**：`steerWarning = lka_state not in (1,3,5)` → 17 命中 →
[controlsd.py] `lat_active = active and not steerWarning ...` → openpilot **直接不发转向 + `steerTempUnavailable` 软退出**。
（注意：把 17/19 加进允许表是**错的**——实测"17 不给 steering"，只是藏了告警、让 openpilot 对故障 EPS 空发命令，已回退。）

**根因（A/B 对照实验铁证）**：
| 断电瞬间 `STEER_REQUEST` | EPS 恢复后 |
|---|---|
| **1**（engaged，LKA 命令进行中被硬断电） | ❌ **17 故障** |
| **0**（先按 CANCEL 干净脱离再断电） | ✅ **1 standby 健康** |

→ **EPS 在"LKA 命令进行中（STEER_REQUEST=1）"被粗暴断电会латch 保护故障 17。** 真 Corolla 熄火有
**优雅关断序列**（摄像头先停 LKA、模块按序休眠、最后断电），单 CAN 去掉摄像头后缺了这个。
openpilot 的"脱离"没有专门终止报文——就是持续的 0x2E4 里把 `STEER_REQUEST`（byte0 bit0）从 1 翻 0、
torque 清零。

**预防**：
- **操作**：熄火/断电/打火前**先按 CANCEL 脱离**（STEER_REQUEST→0）→ EPS 干净回 standby，不进 17。✅ 实测
- **代码**：ECU 已实现**智能门控自动 engage**（`AUTO_ENGAGE_ON_OP=true`）：上电后等
  「openpilot 就绪(收到 0x2E4)」且「真实 EPS 连续处于健康 standby(LKA_STATE==1) ≥3 秒」
  才一次性挂上。EPS 处于故障(如 17)时门控永不就绪，不会自动挂——从根上避免对故障/启动中的 EPS 发命令。

**恢复（已故障时）**：openpilot 不发命令（脱离/自动 engage 关）的前提下，**干净长断电几分钟**（放电）
→ EPS 复位到 standby(1)。✅ 实测。注意：软件重启 EON、快速点火循环**都无法**清掉 17。

> 相关提交：`ac5dff76`（文档 + ECU 默认手动 engage + 0x262 解码修正 + 调试脚本归档）。

### F. ★★★ 横向控制调参 —— 黄金配置（已验证"非常完美"）

修好底层问题后实车试驾（时速到 65km/h，openpilot 激活率 98.7%），**横向控制表现"非常完美"**。
解析该次试驾 rlog 得到并已固化的黄金配置见 §5。

**关键认知**：控制器实际用的 steerRatio 是 **liveParameters 在线学习值（≈18.8）**，不是静态的 14.35
（VehicleModel 取在线值）。已把静态默认也对齐到 18.8（提交 `43b956bf`），即使 LiveParameters 被清，
开机也从接近黄金值起。

## 3. 关键认知纠正（早期文档中已被推翻的结论）

> 这些是过程中走过的弯路，历史文档里仍有记载，**以下为最终正确结论**：

1. **❌「can2e4=0 说明命令没到车侧总线」** → ✅ **错误推理**。panda 的 CAN 控制器**硬件上不会把自己
   发出去的帧回灌到接收流**，所以 openpilot 自己发的 0x2E4 永远不会出现在它自己收到的 `can` 里，
   无论有没有真上总线。正确的 TX 健康指标是 `pandaState.canSendErrs`（被总线 ACK 即发出去了）。

2. **❌「单 CAN 下真实 EPS 在另一条 steering bus / 需要双发 bus0+bus1」** → ✅ **错误**。只有一条物理
   CAN，所有节点并联；EPS、Arduino、panda 都在 bus0。早期"bus0+bus1 双发"的试验已删除，只发 bus0。

3. **❌「EPS 收到命令但拒绝执行，需要车速」** → ✅ **错误**。真因是**命令根本没到 EPS**（§2.D 转发 jam）。
   修复后静止（vEgo=0）时 EPS 就能进 active(5)，静止力矩≈0 是正常的。

4. **❌「真正的瓶颈是 bus-routing / 线束桥接 / minEnableSpeed 门槛」** → ✅ 都不是。瓶颈是
   **Toyota 安全模式强制的 bus0→bus2 摄像头转发在无 bus2 的单 CAN 上把 TX 堵死**。

5. **❌「LKA_STATE 用 `(byte3>>1)&0x7`」** → ✅ 字段是 7 位，应 `&0x7F`（否则 9/17/25 被截断）。

## 6. 日常操作手册

- **挂上自动转向**：**智能门控自动 engage** 已启用——开机后 openpilot 就绪且 EPS 确认健康 standby
  稳定 3 秒，会自动挂上（一次性）。也可手动按 Arduino 的 **MAIN** 按钮 engage/disengage。
- **脱离**：按 **CANCEL**（或再按 MAIN）。
- **⚠️ 打火/熄火/断电前**：**务必先按 CANCEL 脱离**，否则 EPS 会被"命令进行中硬断电"打成故障 17。
- **万一进了 17（steering temporarily unavailable）**：脱离状态下**彻底断电几分钟**再上电（软件重启/
  快速点火循环都无效）。
- **记住**：静止（vEgo=0）时 openpilot 发 0 力矩、方向盘不动，是正常的；要看转向得有车速。
