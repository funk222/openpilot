# openpilot 自定义 Toyota single-CAN 调试总览

> ⚠️ 历史文档（过程记录）。本文中"命令没到车侧总线/can2e4=0 是故障证据/双发 bus"等早期结论
> 已被后续实测推翻——真因是 panda bus0→bus2 转发 jam。最终权威总结见 [最终总结.md](最终总结.md)。

## 一、当前结论

1. 现在最核心的阻塞不是版本号，而是两类独立问题并存：
   - steering command 没有真正到达车侧 EPS 总线
   - panda 断电 / USB 失联后，boardd 不会自动重连，导致 openpilot 进入 `commIssue` / `usbError`，必须重启 EON

2. 现在的关键判断：
   - openpilot 能进入 `enabled` / `active`，说明控制层没有完全坏掉
   - 但 `sc2e4` 在增长，`can2e4` 始终接近 0，说明 command 产生了，但没有看到真实车侧总线帧
   - 这说明 steering 问题已经从“参数/低速门槛”升级到“CAN bus 路由 / 转发 / bridge 层”问题

3. panda 断电后，相机不会自动停，因为 camera 与 panda 是两个独立链路；EON 仍然通电时，摄像头会继续跑到 EON 断电。

4. openpilot 对“通信断开”的判断并不看相机状态，而看：
   - `pandaStates` 是否 valid
   - `can` 是否持续更新
   - `self.sm.valid["pandaStates"]`
   - `self.sm.all_alive_and_valid()`
   - `CS.canValid`

## 二、已确认的关键代码点

### 1) steering 关键判断

- `selfdrive/car/toyota/carcontroller.py`
  - steering command 通过 `create_steer_command(..., bus=...)` 生成
  - 目前单 CAN 分支会广播到多个 bus 候选（0/1/2）做试验

- `selfdrive/car/toyota/toyotacan.py`
  - `STEERING_LKA` 生成在 `0x2E4`

- `selfdrive/debug/steering_watch.py`
  - 自动记录：
    - `state`
    - `enabled`
    - `active`
    - `actSteer`
    - `can2e4`
    - `sc2e4`

### 2) 低速门槛不是主因

- `selfdrive/car/toyota/interface.py`
  - 已强制把 `minEnableSpeed` 设为 `-1`（single-CAN 特判绕过）
  - 仍然没有 steering

- 这说明：
  - 不是低速门槛卡死
  - 也不是 engage 逻辑本身无法进入

### 3) panda 断电后的真实故障逻辑

- `selfdrive/controls/controlsd.py`
  - `elif not self.sm.valid["pandaStates"]:` -> `EventName.usbError`
  - `elif not self.sm.all_alive_and_valid() or self.can_rcv_error:` -> `EventName.commIssue`

- `selfdrive/boardd/boardd.cc`
  - 如果 `connected == false`，boardd 原来会直接退出
  - 这会导致 openpilot 看到“communication issue between processes”

## 三、当前最可能的根因

### 1) steering 卡住：链路问题，不是参数问题

目前最可信的结论：

- openpilot 确实在发 `0x2E4`
- 但 `can2e4` 持续为 0
- 说明命令没有真正到达车侧 EPS 可见总线

因此最可能是以下任一项：

1. 单 CAN 下，真实 EPS 在不同总线
2. Arduino / custom ECU bridge 没有把该帧转发到目标 bus
3. 自定义 CAN 转发/桥接没有把 `STEERING_LKA` 转到真正执行的 bus
4. 车侧 0x2E4 不是在预期总线上存在，导致 openpilot 看不到反馈

### 2) panda 断电：boardd reconnect 缺失

- panda 掉电后，如果 boardd 直接退出，就会导致 EON 需要重启才能恢复
- 这不是 openpilot 进程“卡住”本身，而是底层 panda/USB 连接没有自动重建

## 四、已做的修正

### 1) steering 路由试验

已在：

- `openpilot_nolfs/selfdrive/car/toyota/carcontroller.py`

做法：

- 在 single-CAN 模式下，尝试把 `STEERING_LKA` 广播到多个候选 bus（0/1/2）
- 这是临时验证，不是最终结论

### 2) boardd reconnect 自动修复

已在：

- `openpilot_nolfs/selfdrive/boardd/boardd.cc`

做法：

- 不是在第一次 disconnect 直接 `do_exit = true`
- 改成：失联后清理并进入 reconnect loop
- 这应当允许 panda 断电后自动恢复，不需要整个 EON 重启

### 3) 调试日志工具

已保留：

- `openpilot_nolfs/selfdrive/debug/steering_watch.py`
- `openpilot_nolfs/selfdrive/debug/run_steering_watch.sh`
- `openpilot_nolfs/selfdrive/debug/stop_steering_watch.sh`

用途：

- 连续记录 `state/enabled/active/actSteer` 和 `sc2e4/can2e4`
- 解决“开车后无法实时交互，回来再看日志”的问题

## 六、建议的下一轮调试顺序

1. 在车上做一次短路试：
   - 只观察 `pandaStates` / `can` 是否失效
2. 从 EON SSH 看 steering log：
   - `sc2e4` 是否持续增长
   - `can2e4` 是否仍为 0
3. 若 `can2e4` 仍为 0：
   - 确认真实 EPS bus 路由
   - 更换 bus 试验
4. 若 `can2e4` 变成非 0：
   - 再看 steering 是否真正有执行
5. 单独复测 panda 断电重连：
   - 看 boardd 是否重新连接
   - 若不重连，继续修正 reconnect / USB 逻辑

## 七、最重要的一句话

现在的工程重点已经从 “装系统能不能跑” 转到了两个硬点：

- steering command 是否真的送到了车侧 EPS 总线
- panda 断电后 boardd 是否能自己恢复，不需要重启 EON

这两点是决定你下一次试驾能不能真正 selfdrive 的核心。
